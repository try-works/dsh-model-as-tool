<h2 id="changes-in-this-release">Changes in this release</h2>
<ul>
<li><code>refine</code> is <code>async</code> and takes <code>languageCode</code>; it works on any transcript&#39;s words, not only
<code>SpeechAnalyzer</code> output.</li>
<li>The handle is <code>Align</code>. <code>SpeechTimestampRefiner</code> remains as a deprecated alias for the name
only: <code>Align</code> has no <code>locale:</code> initializer, and both <code>refine</code> and <code>isSupported</code> changed
shape, so a 3.x call site does not compile through it.</li>
<li>Streaming callers move to <code>StreamingRefiner</code>, which wraps an <code>Align</code> and keeps the
<code>SpeechAnalyzer</code> integration. <code>SpeechTimestampRefiner(locale:)</code> no longer compiles.</li>
<li>The Apple runtime&#39;s log-mel frontend is corrected: it scaled power by 4 before the log.
On-device results change at this release.</li>
<li>A LiteRT export adds Linux, Windows and Node.</li>
<li>The npm package is Node-only, and its default entry refuses in the browser with an
actionable error. The refiner is a cascade of two graphs, and the WebAssembly host compiles
one model per module, so there is no browser build.</li>
<li>Three further changes break source on 3.x callers, separately from the two above:
<code>isSupported</code> is now <code>async throws -&gt; Bool</code> and takes a language code rather than being a
property; <code>reset()</code> is no longer on the offline handle; and <code>AlignResourceError</code> is removed.</li>
</ul>

attaches to <code>SpeechAnalyzer</code> (iOS 26 and later) through <code>StreamingRefiner</code>.</p>

<code>try await refiner.isSupported()</code>. On JavaScript, <code>Align.isSupported(language)</code> is a
synchronous check with the same meaning.</p>
<p><code>refine</code> also keeps the original timestamp for any single word whose correction runs into the
search edge, whose corrected range would end before it starts, or, when streaming, whose forward
context is not buffered yet. Those fallbacks are checks on structure, not on accuracy: a
correction that looks plausible but is wrong still lands. A stage that fails outright throws
rather than falling back. See Limitations.</p>
<p>Input that cannot be a time is refused before any work, whatever the language. Every <code>start</code>
and <code>end</code> must be finite and from -1 to 10,000,000 seconds, and the sample rate finite and
positive, and the audio must not be empty. Audio at another rate that resamples to more than
about 37 hours at 16 kHz is refused too. Swift throws <code>AlignError.invalidInput</code>, naming the
word; JavaScript rejects with a <code>RangeError</code>. A word more than about 1.2 seconds past the end
of the audio has nothing to refine against, so it keeps its input times with <code>refined</code>
false.</p>

<h2 id="inputs-and-outputs">Inputs and outputs</h2>
<ul>
<li><strong>Input:</strong> mono audio plus any transcript&#39;s words with their proposed start/end times.</li>
<li><strong>Output:</strong> the same words with corrected start/end times, or the original time when a
correction is not structurally safe.</li>
</ul>
<h2 id="accuracy">Accuracy</h2>
<p>On the clean condition, macro-averaged over the nine languages, Align cuts the proposer&#39;s raw
timing error by roughly two-thirds. Per language it ranges from a third to over three quarters,
and the noisy condition is lower. Both runtimes are scored on <code>gold-en-us</code>, the 258-boundary set
corrected by hand against the waveform. There the on-device Core ML runtime&#39;s corpus mean boundary
error is 44.8 ms (darwin-arm64, 2026-09-21), within 0.2 ms of the same checkpoint through the
training-time frontend (45.0) and less than half the proposer&#39;s 100.8 ms, and the LiteRT export&#39;s
corpus mean boundary error on that set matches the training-time reference to five significant
figures. That is one corpus average in one language, not a per-boundary guarantee. The
per-condition and per-language figures on this page are the training-side measurement; the Apple
runtime&#39;s frontend changed at this release, so on-device Core ML numbers differ from v1.0.0&#39;s and
are not carried over from it. The same per-condition figures are on the
<a href="https://huggingface.co/desert-ant-labs/align">model card</a>, which also names the three
weakest languages.</p>
<h2 id="languages">Languages</h2>
<p>English, Spanish, French, Italian, Portuguese, German, Japanese, Korean, and Chinese. A locale
outside this set is passed through unchanged.</p>
<h2 id="limitations">Limitations</h2>
<ul>
<li>The macro-averaged figures are measured against machine forced-alignment estimates, not human
annotations, so they show a large, consistent reduction of the proposer&#39;s timing error rather
than sample-accurate ground truth.</li>
<li>A learned correction is not guaranteed to improve every boundary; the structural fallback keeps
the original timestamp when a correction looks unsafe but cannot catch every plausible-looking error.</li>
<li>Japanese, Korean, and Chinese were the weakest languages before v1.0.0. They now improve their
proposals by 33%, 55%, and 51%.</li>
<li>Number timings are the weakest remaining case. On a small sample refinement moved digit
boundaries further from the reference than leaving them alone, so treat spoken numbers as
unimproved until a larger sample settles it.</li>
<li>The LiteRT export is a third numeric path alongside Core ML and the training-time reference. The
parity fixture is Core ML&#39;s own recorded output on synthetic audio: Core ML on the CPU
reproduces it where it was measured (0.0 ms, against a 25 ms tolerance) while LiteRT drifts
10.4 ms from it (linux-arm64, 2026-09-17). Treat the two runtimes as able to disagree by around
10 ms on the same audio, not as agreeing to sub-millisecond.</li>
<li>No browser build: the cascade is two graphs, and the WebAssembly host compiles one model per
module.</li>
<li>No Android SDK.</li>
</ul>
