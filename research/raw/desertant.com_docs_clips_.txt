            <p class="docs-index-note docs-index-note--lg">Short clips and highlights from talking video and audio: podcasts, interviews, meetings. On-device.</p>

          </header>

<h2 id="usage">Usage</h2>
<p>Apple, Linux and Windows. Give it a transcript as one sentence per element, in
spoken order, and it returns the best non-overlapping moments, ranked.</p>

<h2 id="maximum-video-length">Maximum video length</h2>
<p>There&#39;s no context window. Clips never reads a transcript whole: sentences run through the
selector in batches of 16 and each candidate clip is scored on its own, so length is bounded by
time rather than by a token limit. The longest we&#39;ve run is an 835 sentence podcast.</p>
<table><thead><tr><th>transcript</th><th>iPhone 17 Pro</th><th>iPhone 15 Pro</th></tr></thead><tbody><tr><td>404 sentences, 25 minutes of video, 12 clips</td><td><strong>9.19s</strong></td><td><strong>10.22s</strong></td></tr>

<p>Measured on device at batch 16, pinned to <code>.cpuAndNeuralEngine</code>.</p>

Function <code>select</code>: <code>ids</code>, <code>mask</code>, <code>disc</code> → <code>saliency</code>, <code>start_<wbr>p</code>, <code>end_<wbr>p</code>. Function <code>score</code>: <code>ids</code>, <code>mask</code> → <code>score</code></td></tr>
<tr><td><code>clips-selector.<wbr>tflite</code></td><td>LiteRT, int8 weight-only</td><td>The selector, for Android, Linux and Windows</td></tr>
<tr><td><code>clips-scorer.<wbr>tflite</code></td><td>LiteRT, int8 weight-only</td><td>The scorer, for Android, Linux and Windows</td></tr>
<tr><td><code>clip_<wbr>tokenizer.<wbr>bin</code></td><td>Unigram tokenizer</td><td>Tokenizer pieces and scores, in the compact binary the runtime reads</td></tr>
<tr><td><code>clips_<wbr>meta.<wbr>json</code></td><td>JSON</td><td>Graph widths, input roles and feature order a runtime needs</td></tr></tbody></table>
<h3 id="reaching-a-function-in-the-core-ml-package">Reaching a function in the Core ML package</h3>
<p>A file path names the package, not the graph. Loading needs
<code>MLModelConfiguration.functionName</code> set to <code>select</code> or <code>score</code>. Without it Core ML loads the
package&#39;s default function and reports nothing, so both halves of the pipeline end up being
the selector.</p>
<h3 id="windows">Windows</h3>
<p>The selector runs at 128 tokens, the scorer at 256, both at a fixed batch of 16 sentences.</p>
<p>A single sentence is truncated to <strong>64</strong> tokens before it reaches the selector, which is not
the same thing as the graph width.</p>
<h2 id="status">Status</h2>
<p>Internal testing. This page carries no quality figures yet.</p>
<blockquote>
<h3 id="the-tflite-files-do-not-work-with-the-desert-ant-sdk-yet-do-not-build-on-them">⚠️ The <code>.tflite</code> files do not work with the Desert Ant SDK yet. Do not build on them.</h3>
<p>The SDK&#39;s LiteRT backend cannot drive them:</p>
<ul>
<li>the graphs name their inputs <code>args_0</code>, <code>args_1</code>, <code>args_2</code> and their outputs <code>output_0…2</code>;
the SDK asks for <code>ids</code>, <code>mask</code>, <code>disc</code> and <code>saliency</code>, <code>start_p</code>, <code>end_p</code>. There is no
mapping layer, so the first call fails.</li>
<li>the graphs take <strong>int64</strong> ids and mask; the SDK builds int32.</li>
<li>the scorer is 256 wide and the SDK&#39;s LiteRT backend cannot report a width, so it falls
back to 128.</li>
</ul>
<p>They are left published because they are honest artifacts and someone driving LiteRT
directly can use them: the shapes and output order are in <code>clips_meta.json</code>. They are
<strong>not</strong> a working Android/Linux/Windows path today.</p>
<p>Also unresolved: this export was measured at ~2.1 GB peak RSS against a 1.6 GB Android
budget.</p>
</blockquote>
<p><strong>The two platforms are not equally evidenced.</strong> The Core ML package has clips that were
generated from it and judged. <strong>No clip has been read from the LiteRT files, on any platform.</strong></p>
<h2 id="requirements">Requirements</h2>
<p>The Core ML package is <strong>specification version 9</strong>: it requires <strong>iOS 18 / macOS 15 / tvOS 18 /
visionOS 2 / watchOS 11</strong>, read off the compiled artifact. Reaching either graph needs
<code>MLModelConfiguration.functionName</code> set to <code>select</code> or <code>score</code>.</p>
<h2 id="limits">Limits</h2>
<p>Behaviour worth knowing before you build on it, stated without figures for the reason above:</p>
<ul>
<li><strong>It under-emits on short video.</strong> Given a short transcript it returns markedly fewer clips
than expected. If your product needs a guaranteed number of
clips from a two-minute video, measure before relying on it.</li>
<li><strong>It emits some dross</strong>, most on podcast-length input. There is no confidence score to
filter on yet: <code>Clip.score</code> ranks within one video and is not calibrated across videos.</li>
<li><strong>The clip limit is a cap, not a quota.</strong> Asking for 10 does not mean receiving 10.</li>
<li><strong>Selection is sensitive to small score changes.</strong> Candidate spans around one moment score
very close together, so a different runtime, compute unit or quantization can return a
different-but-comparable set rather than the same set. Do not treat exact span equality
between two builds as a correctness check.</li>
<li><strong>Non-Latin scripts are under-tested.</strong> The evaluation corpus is overwhelmingly Latin-script.</li>
<li><strong>Duration is a soft prior, not a rule.</strong> Clips may come back shorter or longer than a
typical Short.</li>
</ul>
