# VERIFY.md — runnable verification checklist and prerequisites

**Purpose:** the §21.5 handoff artifact. How to reproduce the full verification from a clean
checkout, how each stage maps to the checklist's §21.3 commands, and where every §21.5 artifact
lives (including the two relocated ones and why).

## Prerequisites

- Windows x64, plain Node (the suites run on `v24.11.0`; direct node paths only —
  `node node_modules/typescript/bin/tsc`, `node --import tsx --test`; the ONE sanctioned npm
  script is `npm run verify`).
- No credentials or model weights required for the main chain (BLOCKED/NOT_RUN is recorded
  where they would be).
- The opt-in qualification runs (`qualify:voz`, `qualify:embeddinggemma`) need the pinned model
  artifacts in the extension caches; without them they degrade with an explicit
  `SKIPPED-artifacts-missing` line (exit 2), never a fake pass.

| Checklist command | Repo script | What it runs |
|---|---|---|

| `test:unit` | `npm run test:unit` | the full multi-package node:test suite (`npm test`) |
| `test:contracts` | `npm run test:contracts` | contracts suite + host contracts-registration |
| `test:extensions` | `npm run test:extensions` | SDK + all extension suites |
| `test:recipes` | `npm run test:recipes` | recipes + declarative-recipes suites |
| `test:integration:dsh` | `npm run test:integration:dsh` | full host suite |
| `test:mcp:2026-07-28` | `npm run test:mcp:2026-07-28` | MCP fixtures probe (39 checks) + live schema (12/12 over a real socket) |
| `test:composition` | `npm run test:composition` | PTC + tool-mode-run + recipes suites |
| `test:models:windows` | `npm run test:models:windows` | tongue/voz/embeddinggemma/needle suites |
| `test:harness:live` | `npm run test:harness:live` | **STATUS REPORTER ONLY** — `scripts/report-suite-status.mjs harness-live` reports the recorded harness-live evidence state. It does NOT run live model calls. Live vision execution over two independently configured DSH vision routes remains **BLOCKED** (recorded in the release gate); do not treat this script name as a live run. |
| `test:security:windows` | `npm run test:security:windows` | authority + ptc-sandbox + SDK install suites |
| `test:packaged:windows` | `npm run test:packaged:windows` | build + verify:built + verify:packed (clean-project tarball probes) |
| `verify:release` | `npm run verify:release [-- --report <path>]` | `scripts/gen-verification.mjs --release-gate`; `--report` writes the machine-readable gate result (`scripts/gen-verification.mjs:23,237-240`) |

The single orchestration entry point is `npm run verify`:
`typecheck && build && npm test && verify:built && verify:packed && verify:architecture &&
verify:mcp && verify:verification && verify:traceability`.

`verify:packed` includes `scripts/check-probe-isolation.mjs` (every probe mount must carry an
isolated `stateFile` — regression guard for the round-67 incident).
`verify:verification` additionally drift-checks the §21.5 artifacts via
`scripts/gen-models-index.mjs --check` (models index current; compatibility.json and
quality-gates.json parse with their required keys).

## TDD notes

- Statuses are PASS / FAIL / BLOCKED / NOT_RUN only (TDD-06); the release gate exits nonzero
  while any mandatory gate is not PASS — red by design.
- Test isolation (TDD-07): suites use throwaway temp fixtures and isolated state files; the
  probe-isolation guard enforces it mechanically.
- Red-run retention (TDD-02): recorded red episodes are listed in
  `verification/tdd-red-evidence.md` with the references that survive; full pre-fix command
  outputs from earlier session rounds were not archived, and the list says so rather than
  inventing entries.
